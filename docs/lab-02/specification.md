# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a responsive Requester-facing TokTickIT MVP that lets a selected Development Requester create, find, inspect, and manage permitted attachments for their own IT support tickets. The selected requester is a test context only; Lab 2 does not implement authentication.

## 2. Stakeholder Request Interpretation

The IT department needs a professional service-desk experience for end users. A requester selects a temporary seeded requester identity, creates a ticket with classification and priority information, receives an official backend-generated Ticket Number, finds tickets in My Tickets, and opens a read-only Ticket Detail view. Requesters may manage permitted attachments, while the system must protect ownership boundaries and provide clear responsive, accessible states.

## 3. Scope

### Included

- PostgreSQL reference data for active Categories, Related Systems, and Development Requesters.
- Temporary Development Requester selection and switching.
- Ticket creation with backend-generated Ticket Number, Ticket Date, and initial `New` status.
- Requester-owned My Tickets with search, filters, sorting, pagination, and pagination metadata.
- Requester-owned read-only Ticket Detail.
- Attachment upload, metadata, active download, and soft removal.
- Backend and frontend validation, ownership checks, safe errors, loading/empty/failure states, responsive UI, accessibility, and Zen Green styling.
- Unit, API/integration, UI, responsive/visual, and E2E test evidence.

### Explicitly Excluded

- Real authentication: login, logout, passwords, password hashing, sessions, tokens, authenticated identities, and real role-based authorization.
- IT Staff dashboards, queues, claiming, reassigning, changing IT Priority, or other staff workflow.
- Public Comments, Internal Notes, and Actions Taken.
- Status changes after initial `New`, including resolving, closing, reopening, cancelling, or resolution confirmation.
- Administrator management of users, Requesters, roles, or reference data.

## 4. Functional Requirements

- FR-01: The system shall load active Categories from PostgreSQL.
- FR-02: The system shall load active Related Systems from PostgreSQL.
- FR-03: The system shall load active Development Requesters from PostgreSQL.
- FR-04: The seed shall contain the four required Categories, at least six Related Systems, at least four active Requesters, and at least one inactive Requester, and shall be idempotent.
- FR-05: The selector shall allow one active Development Requester to become the current test context and shall support switching context.
- FR-06: The Create Ticket screen shall capture Category, Related System, Summary, Requested Priority, Description, and permitted Attachments.
- FR-07: The backend shall generate and persist a unique Ticket Number, Ticket Date, and initial `New` status.
- FR-08: The API shall return persisted ticket values after creation; the client shall not generate authoritative values.
- FR-09: Validation shall run on both client and server, and invalid requests shall not create a Ticket.
- FR-10: The system shall prevent duplicate ticket creation caused by repeated submission or retry of the same operation.
- FR-11: The system shall preserve entered ticket values after a recoverable submission failure.
- FR-12: My Tickets shall return only Tickets owned by the selected Requester.
- FR-13: My Tickets shall support documented search, Category, Related System, Requested Priority, and Status filters.
- FR-14: My Tickets shall support documented sorting, Clear Filters, page controls, and backend pagination metadata.
- FR-15: Ticket Detail shall return one Ticket only when it belongs to the selected Requester.
- FR-16: Ticket Detail shall present ticket fields as read-only and include attachment metadata.
- FR-17: The system shall accept only JPG/JPEG, PNG, WEBP, and PDF attachments, up to 5 MB each and five active attachments per Ticket.
- FR-18: Attachment storage shall use safe generated filenames and shall not expose unsafe filesystem paths.
- FR-19: Attachment upload, metadata, download, and soft removal shall enforce Ticket ownership and attachment state rules.
- FR-20: Soft-removed attachment metadata shall remain visible, but its file shall not be downloadable or previewable.
- FR-21: The UI shall use the Zen Green theme and reusable form, list, badge, validation, loading, empty, error, and responsive conventions on every screen.
- FR-22: The completed application shall provide keyboard-accessible controls, visible focus, and readable desktop, tablet, and mobile layouts.

## 5. Business Rules

- BR-01: Ticket Number is generated by the backend and is unique.
- BR-02: Ticket Date is generated by the backend when the Ticket is created.
- BR-03: A new Ticket starts with Current Status `New`; Lab 2 does not change it afterward.
- BR-04: The Development Requester selector is a testing mechanism, not authentication.
- BR-05: Only active Requesters can be selected.
- BR-06: Switching Requester changes the current context and reloads requester-owned data.
- BR-07: A Ticket belongs to exactly one Requester, Category, and Related System.
- BR-08: A Requester may retrieve only their own Tickets and Attachments.
- BR-09: Missing, inactive, or invalid reference-data IDs are rejected by the backend.
- BR-10: Summary is required after trimming and must be 3-120 characters; Description is required after trimming and must be 10-2000 characters.
- BR-11: Requested Priority must be one of `LOW`, `MEDIUM`, `HIGH`, or `URGENT`.
- BR-12: Client validation is for usability; server validation is authoritative.
- BR-13: A failed create operation must not leave a partially persisted Ticket unless the documented compensation strategy is applied.
- BR-14: A repeated client submission must not create duplicate Tickets for the same logical operation.
- BR-15: List search, filters, sorting, page numbering, and page sizes follow the API contract in `api-spec.md`; invalid values are rejected safely.
- BR-16: Empty results and no matching results are distinct UI states.
- BR-17: Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF.
- BR-18: Each attachment is at most 5 MB, and each Ticket has at most five active Attachments.
- BR-19: The stored filename is generated by the server; the original filename is metadata and is sanitized for display.
- BR-20: A removed Attachment remains as metadata with removal information, but its content cannot be downloaded or previewed.
- BR-21: Only the owning selected Requester may upload, download, or remove a Ticket's Attachments.
- BR-22: Attachment upload failure after Ticket creation follows the documented compensation decision: the Ticket remains saved, the failed file is not represented as active metadata, and the UI reports that the Ticket was created but the attachment was not.
- BR-23: Unsafe internal error details are never returned to the client.
- BR-24: Disabled or busy submit controls cannot be activated while the request is processing.
- BR-25: Every acceptance criterion must map to at least one planned test.

## 6. UI Specification Summary

The application shell contains TokTickIT identity, My Tickets navigation, Create Ticket navigation, current Requester display, Change Requester, and a clear active-page indication. The Requester Selection screen appears until a current Requester exists.

Create Ticket uses read-only styling for Requester, Ticket Number, Ticket Date, and Status. Editable fields use consistent labels, height, required markers, field-level validation, visible focus, and a busy Submit state. Success displays the official Ticket Number and a next action. Attachments show selected, invalid, uploading, active, removed, and unavailable states.

My Tickets provides search, filters, sorting, Clear Filters, pagination, Create Ticket, and a table/card representation appropriate to the viewport. Ticket Detail is read-only and shows ownership-safe ticket data and attachment actions.

All screens use the Zen Green tokens in `ui-spec.md`, support keyboard navigation, avoid color-only meaning, and provide initial, loading, success, validation, empty, no-results, and API-failure states where relevant.

## 7. Data Changes

The Prisma design must add Development Requester, Related System, Ticket, and Attachment concepts while preserving the Lab 1 Category model. At minimum:

- Requester: ID, display name, email, active flag, timestamps.
- Related System: ID, name, active flag, timestamps.
- Ticket: ID, unique Ticket Number, backend Ticket Date, Requester/Category/Related System foreign keys, Summary, Description, Requested Priority, Current Status, timestamps, and duplicate-operation protection data if selected by the approved design.
- Attachment: ID, Ticket foreign key, original/display filename, generated storage key, MIME type, size, created timestamp, removal timestamp/reason, and any uploader/removal metadata required by the approved design.

The final Prisma schema and migration must define nullability, foreign keys, unique constraints, indexes justified for ownership and list queries, enums or reference tables, and soft-removal representation. The selected requester must remain a replaceable Lab 2 context so Lab 3 can introduce authentication without treating the selector as secure identity.

## 8. API Contract

The detailed endpoint contract is in `api-spec.md`. Required capabilities are active reference-data retrieval, ticket creation, requester-owned list and detail retrieval, attachment upload, metadata retrieval, active download, and soft removal. Every endpoint must document success, validation failure, missing resource, ownership failure, unsupported/oversized attachment, conflict, and safe unexpected-error behavior as applicable.

## 9. Acceptance Criteria

- AC-01: Given a fresh database, when the idempotent seed runs repeatedly, then all required reference data exists without duplicates and inactive Requesters are not selectable.
- AC-02: Given active Requesters are available, when one is selected, then the application enters the shell and displays that Requester as the current testing context.
- AC-03: Given valid ticket data, when the Requester submits once, then one Ticket is persisted with backend-generated unique Number and Date and status `New`.
- AC-04: Given invalid or missing ticket data, when submission is attempted, then field-level errors appear and no Ticket is created.
- AC-05: Given a repeated submission or retry, when the same logical create operation is processed, then duplicate Tickets are not created.
- AC-06: Given the create API fails, when the error is shown, then safe messaging appears and entered values remain available for correction/retry.
- AC-07: Given Requester A is selected, when My Tickets loads, then only Requester A's Tickets and correct backend pagination metadata are returned.
- AC-08: Given tickets exist, when search, each documented filter, sorting, Clear Filters, and pagination are used, then the list matches the selected query and state messages are correct.
- AC-09: Given Requester B is selected, when Requester A's Ticket is requested directly, then the API does not return the Ticket.
- AC-10: Given a permitted attachment, when it is uploaded, then metadata is persisted and it can be downloaded only by its owning Requester while active.
- AC-11: Given an invalid type, oversized file, or fifth-active-limit violation, when upload is attempted, then the operation is rejected safely by the relevant frontend and backend validation.
- AC-12: Given an owned active Attachment, when it is soft-removed with the required reason, then metadata remains visible and download/preview is blocked.
- AC-13: Given a Ticket creation succeeds but an attachment upload fails, when the result is displayed, then the Ticket remains consistent and the failed attachment is not shown as active.
- AC-14: Given any supported viewport and keyboard-only interaction, when the requester uses the application, then layouts remain usable, focus is visible, and controls have accessible names.
- AC-15: Given the final main branch, when documented checks run, then all planned tests pass and each criterion has traceable evidence.

## 10. Definition of Done

- Approved specification, API, UI, and test-plan documents exist before implementation is declared complete.
- All in-scope acceptance criteria are implemented and mapped to passing evidence.
- No required test is skipped, disabled, flaky, or unrelated to the criterion it claims to prove.
- Database migrations and repeatable seed behavior work from documented setup steps.
- Backend ownership, validation, safe errors, and attachment lifecycle rules are tested.
- Frontend states, accessibility, responsive layouts, and Zen Green styling are checked.
- Unit, API/integration, UI, responsive/visual, and E2E tests pass from documented commands.
- README setup and usage instructions are current.
- Peer review, review responses, screenshots, and final PDF evidence are complete.
- The coding agent does not merge or approve its own work; a human peer approves each PR.

## 11. Assumptions and Decisions

- Lab 1 Categories remain the source of the four required category records.
- Summary/Description limits are 3-120 and 10-2000 characters; priority values are `LOW`, `MEDIUM`, `HIGH`, and `URGENT`. List query names and page sizes are defined in `api-spec.md`; storage and attachment removal-reason wording remain for Issue 6.
- Ticket creation and attachment upload may be separate API operations. The approved compensation behavior is the Ticket remains saved when a later attachment upload fails, with no false active attachment metadata.
- A local/private storage adapter is acceptable for Lab 2 if its generated keys, safe filenames, and download authorization are documented; cloud storage is not required.
- The selected Requester ID is a client testing context and must be passed/validated consistently in the API contract; it is not proof of identity.
